# Architecture

Living document. Updated at the end of every milestone.

## Overview

HifzFlow is a Next.js App Router application backed by Supabase (PostgreSQL,
Auth, Row Level Security). It renders on the server by default, mutates through
Server Actions, and pushes authorisation into the database rather than the
application layer.

```
Browser ──▶ Next.js (Vercel)
              ├── Server Components ──▶ Supabase Postgres (RLS enforced)
              ├── Server Actions ─────▶ Supabase Postgres (RLS enforced)
              └── Route Handlers ─────▶ health, webhooks, cron
```

## Decisions

### D1 — The ayah is the canonical unit

A user's memorisation is stored as ranges over a global ayah index
(1–6,236). Pages, surahs, juz', hizb and rub' al-hizb are **derived views**,
never independently stored state.

*Why:* storing progress separately per unit guarantees drift. A page can begin
mid-surah and a juz' can begin mid-page, so any two independent counters
eventually disagree, and there is no principled way to decide which is right.
One source of truth removes the class of bug entirely.

*Cost:* every display unit requires a join against the reference table. This is
cheap — the reference data is static, small and heavily indexed.

### D2 — Range types with an exclusion constraint

Memorised segments are stored as `int4range` with a GiST exclusion constraint
on `(user_id, ayah_range)`.

*Why:* overlapping segments become impossible at the database level rather than
being prevented by application code that can be bypassed. Range containment and
overlap queries are then index-backed rather than computed in application code.

### D3 — Mushaf editions are data, not constants

Page numbers are meaningful only relative to an edition. Madani 604 is seeded as
the default; Mushaf Malaysia and others are rows added later.

*Why:* hard-coding one edition's pagination bakes a single institution's
convention into every user's records, and correcting it later means migrating
user data rather than inserting a row.

### D4 — Cycle scheduler with a spaced-repetition overlay

Murajaah is generated by a contiguous rotation over memorised content, with
weak passages pulled forward on top of it and daily volume smoothed.

*Why:* pure SM-2 treats passages as independent cards. Huffaz recite contiguous
blocks, so card-optimal scheduling produces a queue that is theoretically sound
and practically unusable. The hybrid keeps the ergonomics of a traditional
rotation while still prioritising what is actually weak.

### D5 — Offline-ready schema from the start

Client-generated UUID primary keys, `updated_at` on every table, soft deletes.

*Why:* offline sync ships late, but retrofitting these three things means
migrating every table. They cost nothing now.

### D6 — Server-first state

Server Components for reads. Server Actions for mutations. TanStack Query only
where optimistic updates genuinely matter (tracking, review queue). `nuqs` for
filter and date state so views are linkable. No global client store.

*Why:* the simplest thing that still survives adding offline sync.

### D7 — Features expose two barrels, not one

Every feature has `index.ts` (client-safe) and `server.ts` (server-only).

*Why:* a single barrel that re-exports both a Server Action and a `server-only`
query will drag the query into the browser bundle as soon as one Client
Component imports the action. That fails the build rather than shipping
silently, but only because the split exists to make the boundary explicit.

### D8 — Auth responses do not reveal whether an account exists

Sign-in reports one message for both unknown addresses and wrong passwords.
Sign-up and password reset report success regardless.

*Why:* differing responses turn any of these forms into an account-enumeration
oracle — an attacker can harvest which addresses are registered without ever
signing in. The cost is a slightly less specific error message.

### D9 — RLS policies check ownership, never lifecycle

A policy answers "is this row mine". Filtering soft-deleted rows happens in
views and feature queries.

*Why:* PostgreSQL validates the updated row against the SELECT policy during an
UPDATE, so `using (owner and deleted_at is null)` makes soft delete impossible —
the policy rejects the very statement that sets the flag. Found by the RLS test
suite; corrected in migration 0004. Full account in `docs/DATABASE.md`.

### D10 — Reference data is generated, checksummed and committed

The Quran index is produced by `scripts/generate-quran-reference.mjs` from
`quran-meta`, validated by 46,406 assertions, and committed with a SHA-256.

*Why:* the application must never fetch reference data at runtime. A network
dependency in the hot path of a memorisation tracker is unacceptable, and
reference data that shifts underneath you silently invalidates every user's
records. The checksum turns a hand-edit or a bad merge into a failed build.

### D11 — Multi-statement writes live in the database

`record_memorisation` and `remove_memorisation` are PostgreSQL functions, not
application code.

*Why:* recording a range that partially overlaps existing coverage must insert
only the gaps; removing from the middle of a segment must split it in two and
carry its metadata to both halves. Both are multi-statement. Driving them from
the client leaves a window in which a segment has been deleted but its
remainder has not yet been written, and a crash in that window loses data.

They are `SECURITY INVOKER`, deliberately — they run as the caller so RLS still
applies. A `SECURITY DEFINER` function here would be an authorisation bypass
wearing a helpful name. A test asserts one user's wholesale removal leaves
another user untouched.

### D12 — `useOptimistic`, not a client cache

Optimistic updates use React's `useOptimistic` with Server Actions.

*Why:* this reverses the earlier plan to use TanStack Query for the tracking
grid. A client cache would mean a provider, a dependency and a second source of
truth living alongside the RSC data. `useOptimistic` covers the one case that
needed it — toggling a page should not wait for a round trip — and discards its
optimistic value automatically when the action settles, so a failed write snaps
back to the server's truth without reconciliation code.

### D13 — Murajaah follows sabaq / sabqi / manzil, not generic SRS

Review is organised into recent-consolidation (sabqi) and long-rotation
(manzil) tiers, with weak passages layered on top. The manzil rotation advances
through a stored cursor.

*Why:* huffaz recite contiguous blocks. A card-optimal SM-2 scheduler produces
queues like "page 12, page 340, page 89" — theoretically sound and physically
unrecitable. The cursor is what makes a day's review a sequence rather than a
shuffle. The tier names are the ones tahfiz programmes already use, so the
model needs no translation for its users.

Weak pages are capped at a third of the daily budget. Without the cap, a user
with fifty weak pages sees nothing but weak pages forever and the rotation
silently stops being a rotation.

### D14 — The daily queue is persisted, not derived

`review_queues` and `review_queue_items` are written once per day.

*Why:* a queue derived from the cursor rearranges itself as items are
completed, so the plan shifts under the person working through it. Persisting
it also makes "overdue" knowable at all, and turns what was scheduled into
history worth keeping.

### D15 — Every date is the user's own

Queue dates and streaks resolve against `profiles.timezone`, never the
server's clock.

*Why:* this is the payoff for capturing timezone at signup. Computed in UTC, a
user in Kuala Lumpur receives tomorrow's queue at 8am and watches their streak
reset for no visible reason.

### D16 — The heatmap is hand-built SVG, not a charting library

`ActivityHeatmap` renders raw `<rect>` elements with native `<title>` tooltips.

*Why:* Recharts has no calendar layout. Forcing one out of a scatter plot
produces worse output than a few hundred rects, and the native `<title>` gives
an accessible tooltip with no JavaScript at all. Recharts still earns its place
for the time-series work in the analytics milestone; this is simply not what it
is for.

Activity thresholds are absolute rather than relative to the user's own
average. A relative scale re-shades the whole history whenever someone has a
heavy week, so a year-old square changes colour for no reason they can see.

### D17 — Goals project from observed pace, not intended pace

`v_goal_progress` computes required pace from what remains, and the projected
completion date from the last fortnight of actual recorded work.

*Why:* a goal that reports "on track" because the plan says four pages a day,
while nothing has been recorded for three weeks, converts a missed target into
a surprise. The baseline — how much of the scope was already memorised when
the goal was set — is frozen at creation for the same reason: recomputing it
would let progress silently reset.

At zero observed pace there is no projected date, and the goal says so. That is
more useful than an infinite one.

### D18 — Column privileges need a table-level revoke first

`revoke update (col) ... from authenticated` is a **no-op** when the role holds
table-level UPDATE, which `authenticated` does through Supabase's default
grants. The narrow revoke has nothing to subtract from and fails silently.

Migration 0010 corrects every table to the form that holds: revoke the table
privilege, then grant back only the writable columns. Row policies were never
affected — no user could reach another user's rows at any point — but the
second layer that stops a compromised client rewriting its own audit columns
was inert from milestone 2 until it was asserted rather than assumed.

### D19 — Strength requires evidence, not just a high rating

`v_page_strength` weights the most recent rating two to one against the
historical mean, and flags pages with fewer than three reviews as
`is_measured = false`. Those pages are excluded from the strongest and weakest
rankings entirely.

*Why:* a page reviewed once and rated five is not stronger than one reviewed
twenty times averaging four and a half — it is less measured. Ranking it makes
the list a record of luck rather than of recall. Recency weighting exists for
the mirror case: a page rated two last week is weak now, whatever it was a year
ago.

### D20 — Recharts for time series, not for everything

Recharts renders the growth area chart and the composed volume-plus-confidence
chart. The activity heatmap stays hand-built SVG.

*Cost:* the analytics route is around 306 kB first load, most of it Recharts. It
is one route, client-rendered and code-split by the router, so the rest of the
app is unaffected — but it is the heaviest page in the project and worth
revisiting if it ever needs to be the landing surface.

### D21 — Locale by cookie and profile, not by route

`next-intl` is wired without a `[locale]` URL segment. The cookie is read at
request time; the profile holds the durable preference and is written alongside
it.

*Why:* a routed locale restructures the entire route tree and buys SEO benefits
that matter for marketing pages, not for an authenticated tool. That cost would
be paid on every future route. The cookie is what makes the change take effect
on the next render without a database round trip; the profile is what makes a
new device pick up the right language on first load.

**Translation is incremental, and deliberately so.** Navigation, settings and
auth are translated; the remaining screens fall back to English. Translating
nine milestones of UI in one pass would produce unreviewed Malay, particularly
for religious terminology, and half-checked strings are worse than an honest
fallback. `src/i18n/messages.test.ts` asserts catalogue parity so a new English
string cannot silently leave the other locale showing a raw key.

### D22 — Theme is not in the database

`next-themes` persists theme to localStorage.

*Why:* it is applied before first paint. Storing it server-side means a round
trip before the correct theme is known, so the flash of the wrong theme returns
— and the only thing gained is cross-device sync of a setting people set once
per device. A bad trade, so it was not made.

### D23 — Account deletion is deletion

`delete_my_account()` removes the `auth.users` row, which cascades through every
table.

*Why:* someone asking to be deleted is asking for deletion. Offering a soft
delete instead, while retaining their records, would misrepresent what the
button does. It is the one `SECURITY DEFINER` function in the schema, and it is
safe for a specific reason: it takes **no arguments** and removes exactly
`auth.uid()`, so there is no parameter through which a caller could name someone
else. A test asserts no argument-accepting overload exists.

### D24 — The service worker never touches writes

Only GET requests are served from cache. Server Actions, auth callbacks and RPC
calls pass straight through.

*Why:* a POST replayed by a service worker is a POST the application does not
know happened, and reconciling that is worse than the problem it solves.
Offline writes are handled one layer up, in the outbox, where they are visible
to the user and retried deliberately.

The caching strategy is per resource class rather than uniform, which is the
reason this worker is hand-written rather than generated: build output and Quran
reference data are immutable and cached indefinitely; everything else is
network-first with a cached fallback so the app opens offline showing what it
last knew.

### D25 — Replay safety comes from the database, not the client

The outbox can send a queued write twice without harm, because
`complete_queue_item()` returns the existing session when an item is already
complete and `record_pages()` inserts only the gaps.

*Why worth stating:* this was not arranged for offline. Both functions were
written that way in milestones 4 and 5 for their own reasons, and it is what
makes replay tractable now. Without idempotent writes this would need
server-side deduplication keys and a great deal more care.

Entries are replayed **sequentially**, oldest first. Firing them in parallel
would let a later rating land before an earlier one.

### D26 — A failed write is queued, not discarded

`navigator.onLine` reports true for a captive portal or a router with no
upstream, so it is treated as a hint. Every write attempts the network first and
falls back to the outbox on failure, which means a wrong answer from the browser
costs a retry rather than losing the user's work.

### D27 — Rate limiting in PostgreSQL, not Redis

`consume_rate_limit()` is a fixed-window counter in the database, keyed by a
salted hash computed in the application.

*Why:* an in-memory counter is useless on serverless — instances share no state,
so the limit becomes "N per instance", which is no limit. Redis works but adds a
service, two secrets and another thing that can be down, and the write volume of
a few auth endpoints does not justify it. The database is already here, already
transactional, and already what the attacker is trying to reach.

Two limits per attempt — identifier and IP — because either alone is trivially
defeated. The limiter **fails open**: a database hiccup that locked everyone out
of sign-in would be worse than a brief window with no application-level limiting,
and Supabase Auth's own limits sit underneath.

The bucket is hashed in the application so the counter table never holds an email
or an IP. It is one of very few tables the anonymous role can reach at all.

### D28 — Function EXECUTE must be revoked from PUBLIC

PostgreSQL grants EXECUTE on every new function to `PUBLIC`. Revoking from named
roles leaves that grant in place, exactly as a column-level UPDATE revoke does
nothing against a table-level grant.

For a `SECURITY DEFINER` function that grant is the difference between a helper
and a privilege escalation, and it is applied silently at creation. A test now
asserts that no definer function is PUBLIC-executable apart from the two that
must be.

This is the third instance of the same class of mistake in this project — a
security property asserted rather than verified, defeated by a default that fails
quietly. The others are D9 and D18.

### D29 — CSP carries a per-request nonce, generated in middleware

*Why middleware:* the header and the scripts it authorises must share a nonce, and
only middleware sees both. It is forwarded on the request so Next.js attaches it
to its own scripts and the layout can pass it to `next-themes`, whose inline
theme script would otherwise be blocked and reintroduce the flash it exists to
prevent.

Two compromises, documented in `src/lib/security/csp.ts` rather than hidden:
`style-src 'unsafe-inline'`, because React writes style attributes and there is no
nonce mechanism for them — the alternative is no policy at all; and
`'strict-dynamic'`, because Next loads chunks from scripts rather than markup, and
that is stronger than allow-listing a CDN by hostname.

## Directory structure

```
src/
├── app/            Routes only. Thin: resolve params, check auth, render.
├── features/       Vertical slices. See src/features/README.md.
├── components/     Cross-feature UI.
│   ├── ui/         shadcn/ui primitives.
│   ├── providers/  Context providers.
│   └── brand/      Logo and brand marks.
├── lib/            Framework-agnostic helpers, env, constants.
├── hooks/          Cross-feature client hooks.
└── types/          Cross-feature types.
```

## Design tokens

All colour lives in `src/app/globals.css` as CSS custom properties with light
and dark values. Components reference tokens, never raw colours. Beyond the
shadcn base, the system defines:

- **State tokens** (`--state-new` … `--state-overdue`) — the five states a
  passage can occupy, so status colour is defined once.
- **Density ramp** (`--hifz-0` … `--hifz-4`) — five steps driving the activity
  heatmap and the whole-mushaf density strip.

`/design-system` renders every token and component. It is a real route, kept
current as the system grows.
